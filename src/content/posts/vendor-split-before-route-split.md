티켓 제목은 이랬다. **"프론트 파일 10MB 초과로 CloudFront 캐시 제외 현상 해소를 위한 페이지 단위 코드 스플리팅 적용."**

전날 인프라를 맡은 동료가 팀 채널에 메인 JS가 10MB를 넘었다고 알렸고, 나는 "코드 스플릿은 우선 간단하게 페이지(라우트) 단위로만 적용해 볼까 한다, 하루이틀 걸릴 것 같다"고 답해 둔 상태였다. 할 일도 정해져 있었고 방법도 정해져 있었다.

그런데 작업을 시작하면서 처음 든 생각은 코드가 아니라 질문이었다.

## 캐시가 실패했다는 건 어떻게 알지

> 근데 나 궁금한 게, 이게 CloudFront 캐시랑 어떤 연관이 있지? 1번, 캐시가 실패했다는 건 어떻게 알 수 있지? 2번, 그렇다면 코드 스플리팅을 하면 경로마다 캐시가 가능한가?

우리 앱은 SPA라서 어느 경로로 들어오든 같은 `index-xxx.js`를 받는다. 이 파일이 10MB를 넘어서 캐시가 안 된다면 모든 사용자가 매번 오리진까지 간다는 얘기다. 그게 사실이면 꽤 큰 문제였는데, 확인해 본 적은 없었다.

그래서 live에 접속해 개발자 도구로 메인 번들 응답을 직접 열어 봤다.

![메인 번들 응답 헤더 — X-Cache: Hit, Content-Encoding: gzip](TODO)

- `X-Cache: Hit` — **캐시는 되고 있었다.**
- `Content-Encoding: gzip`, 11MB 파일이 약 2.86MB로 전송됐다.
- `ETag`가 nginx 형식이었다. 압축한 주체는 CloudFront가 아니라 **오리진의 nginx**였다.

알고 보니 CloudFront의 자동 압축은 1KB~10MB 파일에만 걸린다. 10MB를 넘은 메인 번들은 엣지에서 압축되지 않았고, 동료는 그 대응으로 nginx에서 gzip을 켜 둔 것이었다. 동료가 처음 쓴 말도 "10MB 넘어서 **자동 압축**을 안 해 준다"였다. "캐시 제외"는 티켓으로 옮기면서 생긴 오기였다.

솔직히 이때 나는 nginx가 파일을 서빙만 하는 줄 알았다. 압축까지 해서 보내 준다는 건 이번에 처음 알았다.

## 내가 이해한 걸 소리 내서 읊어 봤다

헤더 몇 개 보고 "아 그렇구나" 하고 넘어가면 나중에 다시 헷갈릴 것 같았다. 그래서 내가 이해한 흐름을 처음부터 말로 풀어 봤다.

> 빌드하면 index-xxx.js가 11MB쯤 된다. A 사용자가 배포 후 처음 요청하면 nginx가 이걸 주고, CloudFront는 11MB짜리를 받아 캐시하고 A에게 보낸다. 이후 B 사용자는 CloudFront 캐시에서 받으니까 nginx까지 안 간다.

여기까지는 맞았다. 틀린 건 그다음이었다. 나는 "캐시가 안 되니까 무조건 nginx까지 간다"를 문제로 이해하고 있었는데, 실제 문제는 **압축이 안 된 11MB가 캐시되고, 모든 사용자가 그 11MB를 받는다**는 것이었다. 동료가 걱정한 것도 그쪽이었다.

그렇게 정리하고 나니 질문이 하나 더 생겼다.

> 근데 이런 관점이면 번들링이 굳이 필요한 느낌은 아니네? nginx에서 압축하나 엣지에서 압축하나, 어차피 브라우저에서 압축 푸는 건 똑같은 거 아님?

지금은 nginx gzip이 켜져 있으니 당장 전송량 문제는 없다. 그럼 코드 스플리팅으로 얻는 게 뭘까. 따져 보니 이유는 "10MB 미만"이 아니었다.

- **배포 후 재다운로드.** 한 줄만 고쳐도 해시가 바뀌어서 사용자는 다음 날 11MB를 통째로 다시 받는다.
- **첫 방문 전송량과 파싱 시간.** 신규 사용자는 첫 화면에 필요 없는 코드까지 전부 받고 실행한다.
- **압축을 원래 자리로 돌리기.** 모든 파일이 10MB 아래로 내려가면 nginx의 임시 gzip을 걷고 CloudFront 엣지 압축(br)으로 돌아갈 수 있다. 실측해 보니 같은 파일을 brotli로 압축하면 gzip보다 13% 정도 작았다.

작업은 그대로 하기로 했다. 다만 목표를 "10MB 미만"에서 **"캐시 단위를 쪼개 재다운로드와 첫 진입 비용을 줄이고, 압축을 엣지로 돌린다"**로 다시 적었다.

## 생각보다 많이 깨질 것 같았다

원래 계획대로 페이지 단위 `route.lazy`를 적용하려고 확인할 항목을 뽑아 보니 열아홉 개가 나왔다. 언어를 바꿀 때 번역이 제대로 바뀌는지, 카카오톡 공유 링크처럼 깊은 경로로 바로 들어와도 괜찮은지, 앱을 열어 둔 채 배포되면 옛 청크가 404가 나지 않는지.

> 야 근데 보니까 엄청 깨질 수 있는 거 같은데, 별로 추천 안 하는 변경이냐? 생각보다 많이 깨질 수 있는 거 같아서.

여기서 멈추고 번들이 실제로 무엇으로 채워져 있는지 소스맵으로 나눠 봤다.

| 묶음 | 크기 |
|---|---|
| 외부 라이브러리 (react, MUI, 차트, PDF 생성, 전화번호 검증 등) | **5.13MB (52%)** |
| 건강 기록 / 습관 화면 | 0.89MB / 0.42MB |
| **원래 1차로 쪼개려던 메뉴 네 개 합계** | **약 0.16MB** |

계획서에 "2.6MB"라고 적혀 있던 메뉴들은 이미지와 테스트까지 포함한 소스 폴더 크기였다. minify된 실제 코드는 0.16MB였다. 1차를 다 해도 메인 번들은 2%밖에 안 줄고, 배포 중 옛 청크 404 같은 위험은 첫 단계부터 그대로 진다. **위험은 다 지고 효과는 거의 없는 구성**이었다.

페이지 단위가 효과가 없다는 뜻은 아니었다. 무거운 건 대부분 특정 화면만 쓰는 라이브러리라서, 그 화면을 떼면 라이브러리도 같이 빠진다. 기준을 **"어느 메뉴냐"에서 "무엇을 끌고 오느냐"**로 바꿔야 했다.

## 순서를 바꿨다: vendor부터

조건은 하나 걸었다. **기존 동작에 영향이 적어야 한다.** 그래서 위험이 작은 것부터 순서를 다시 짰다.

1. **vendor 분리** — `manualChunks`로 앱 시작에 필요한 라이브러리를 별도 파일로 묶는다. 화면 코드를 언제 받는지는 그대로이고 파일만 나뉜다.
2. **버튼을 누를 때 라이브러리 받기** — PDF 생성, 화면 캡처처럼 특정 버튼에서만 쓰는 라이브러리는 그 시점에 `import()`.
3. **무거운 화면만 lazy** — 차트 라이브러리를 끌고 오는 화면만 `route.lazy`.

1단계에서 `node_modules`를 통째로 vendor에 넣지 않은 게 핵심이었다. 그러면 차트·PDF 라이브러리까지 시작 청크에 들어가서 2·3단계의 효과가 사라진다. 그래서 **엔트리에서 정적 import로 닿는 라이브러리만** vendor로 보내는 규칙을 넣었다.

```js
// 엔트리에서 정적 import로 닿는 모듈인지 (동적 import로만 쓰이는 모듈은 false)
const isStaticallyReachable = (id, getModuleInfo, seen = new Set()) => {
  // importers를 거슬러 올라가며 엔트리에 닿는지 확인한다
};

manualChunks(id, { getModuleInfo }) {
  if (id.includes('node_modules') && !id.endsWith('.css')
      && isStaticallyReachable(id, getModuleInfo)) {
    return 'vendor';
  }
}
```

이 부분은 솔직히 어려웠다. 나는 처음에 우리가 쓴 `App.jsx` 같은 코드가 이 함수 인자로 넘어오는 줄 알았다. 실제로는 Rollup이 모듈 그래프를 만든 뒤 **모듈 하나하나의 경로를 `id`로 넘기고**, 함수는 그 모듈이 어느 청크에 갈지만 답한다. 라인 단위로 설명을 듣고 나서야 이해가 됐고, 주석은 내가 이해한 말로 직접 고쳐 썼다. 내가 설명하지 못하는 설정을 머지하고 싶지 않았다.

결과는 이렇다. **index 4.8MB + vendor 5.2MB.** 10MB를 넘는 파일이 없어졌다. vendor는 라이브러리 버전을 올리지 않는 한 해시가 그대로라서, 배포 다음 날 재방문한 사용자는 앱 코드 쪽만 다시 받는다.

## 확인할 건 성능이 아니라 기능이었다

로컬과 개발 서버는 CloudFront를 거치지 않는다. 그래서 거기서 성능을 재는 건 의미가 없다고 봤고, **기능이 깨지지 않았는지만** 확인하기로 했다. 처음에 걱정한 번역 전환과 공유 링크 직접 진입을 중심으로 체크리스트를 만들었다.

PR 미리보기와 개발 서버를 같은 계정으로 띄워 50개 경로를 비교했다. 다르게 나온 곳은 전부 원인이 따로 있었다(미리보기 빌드에 기능 플래그가 빠져 있었다). 머지한 뒤에는 폰으로 건강검진 연동 같은 주요 흐름을 직접 돌려 봤다. 이번 변경은 실행 순서를 그대로 두고 파일만 나눈 것이라, 깨진다면 앱이 시작부터 하얗게 죽는 형태일 거라고 예상했다. 그런 일은 없었다.

그래도 개발 서버에서 일주일을 지켜본 뒤 정기 배포에 넣었다. 언어 팩을 중간에 바꾸거나 메신저 링크로 바로 들어오는 경로처럼, 브라우저 점검으로는 다 못 본 곳이 남아 있었기 때문이다.

## 알게 된 것

같은 날 동료가 사내 다른 프로젝트의 메인 JS도 13.8MB라며 같은 작업을 부탁했고, 그쪽에도 vendor 분리를 넣었다. 동료는 이어서 **빌드 결과에 10MB를 넘는 파일이 있으면 빌드를 실패시키는 규칙**을 공통 빌드 워크플로에 넣었다. 한 번 고치고 끝나는 게 아니라 다시 넘지 않게 막는 쪽으로 이어진 셈이다.

돌아보면 세 번 생각이 바뀌었다.

- 캐시 문제라고 들었는데, 열어 보니 **압축** 문제였다.
- 10MB 아래로 내리는 게 목표인 줄 알았는데, 실제로 얻을 건 **캐시 단위**였다.
- 페이지 단위로 쪼개겠다고 말해 놨는데, 숫자를 보니 쪼갤 곳은 **라이브러리**였다.

세 번 모두 처음 판단은 그럴듯했고, 바꾼 계기는 직접 열어 본 숫자였다. 헤더 세 줄과 소스맵 표 하나가 없었다면 나는 계획서대로 메뉴 네 개를 떼고, 2%를 줄이고, 배포 위험만 떠안았을 것이다.

하나 더 남는 건, 이번 작업을 하면서 **프론트가 빌드돼서 사용자에게 도착하기까지의 과정**이 처음으로 머릿속에 그려졌다는 것이다. 번들러가 모듈을 어떻게 상자에 담는지, 그 상자가 nginx와 CDN을 지나며 어디서 압축되고 캐시되는지. 그리고 라이브러리를 따로 묶어 두는 건 어떤 프로젝트든 처음부터 해 두면 좋겠다는 생각이 들었다.
